# COMP 3110 — Source Code Line Tracker

## Purpose

Line Tracker compares two versions of a UTF-8 source file and identifies corresponding original line numbers. It supports unchanged lines, moved lines, edited lines and exact wrapping of one old line into two through four new lines. Unmatched old and new lines are listed separately. The application includes a command-line interface and a JavaFX desktop interface using the same Java comparison core.

## Design and implementation

The source reader retains original text and one-based line numbers. Comparison copies are lowercased and Unicode whitespace is collapsed. A longest common subsequence establishes ordered equal-line anchors. Advanced matching ranks unmatched candidates with SimHash, combines normalized Levenshtein content similarity with neighboring-token cosine similarity, and resolves competing mappings deterministically. Exact moves are accepted before split reconstruction and fuzzy edited-line matches. The normal weights are 60% content and 40% context; the default acceptance threshold is 0.65.

The shared pipeline validates the requested configuration and complete, exclusive line ownership. The desktop compares immutable source snapshots in a background task. This keeps displayed lines consistent with the comparison and avoids doing matching on the JavaFX event thread. Text exports contain sorted `old-new` pairs; JSON retains group type, scores, unmatched lines and effective settings. Both interfaces use the same formatters. Creating an export refuses an existing destination, including an input file.

Native packages contain the application, pinned JavaFX libraries and an operating-system-specific Java 17 runtime. Separate desktop and CLI launchers use paths relative to the extracted package. Provenance identifies the source commit, dirty state, runtime, platform and artifact checksums. Each operating system must build and test its own package; a package for one platform is not portable to another.

## Dataset and evaluation method

The new dataset contains 25 distinct real source-file pairs with project/revision/license provenance and preserved source hashes. Twenty cases form the development partition; five reserved cases come from separate projects. Seven synthetic fixtures are tracked separately and do not count toward the 25-file requirement. Integration preserved both the foundation's three-line identity fixture and QA's different two-line identity fixture under distinct paths.

Expected mappings are source annotations, not predictions generated by the matcher. Dataset metadata links the recorded source reviews, including the explicitly AI-assisted review performed for Ayden. An annotation review is distinct from final release approval. Both interfaces share source-pinned defaults; evaluation uses the recorded defaults and explicit resource profile. The reserved partition is not used to tune thresholds.

Evaluation expands groups into old/new pairs and reports micro precision, recall and F1, plus per-case results and exact split-group recovery. Baseline and advanced runs are kept separate. Development scores can be dominated by larger, mostly unchanged files, so reserved-test results are reported separately. The existing benchmark has sparse references and is scored by its separate adapter; its numbers are not directly interchangeable with complete new-dataset annotations.

Advanced mode recovered 5 of 15 annotated development split groups and the one synthetic split group. There are no annotated splits in the reserved partition, so it provides no independent split-accuracy estimate. On the reserved set, advanced mode found 74 of 82 expected pairs, compared with baseline's 57. This is useful evidence of improved recall on these cases, not a general accuracy guarantee; only five projects are represented in that partition.

## Historical bug example

A reproducible history investigation follows a Unicode boundary-whitespace defect from the initial implementation through its fix. The same input yields no unchanged pair at the introducing implementation and fix parent, then one correct pair after whitespace collapse is moved before stripping. The script compiles each exact historical snapshot independently. [BUG_TRACING_EXAMPLE.md](BUG_TRACING_EXAMPLE.md) documents the evidence, blame ambiguity and limits. This small example is not a general SZZ implementation; its course acceptance remains unconfirmed.

## Limitations

Normalization can hide case and whitespace differences inside strings and comments. Matches describe textual correspondence, not semantic equivalence or independently proven edit history. Candidate pruning and greedy selection can miss valid alternatives. Exact splits do not handle arbitrary edits or more than four fragments, and the model has no general many-to-one merge operation.

LCS uses quadratic time and table memory. The default four-million-cell guard rejects oversized comparisons. An explicit eight-million-cell benchmark profile increases the resource allowance without changing similarity thresholds; it must be declared consistently in both modes. The current evidence is a candidate for team review, not proof of submission, instructor acceptance or unrestricted accuracy.
